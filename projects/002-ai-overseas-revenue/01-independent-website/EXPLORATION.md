# 独立站探索｜字幕交付前的音频对齐

这个子项目探索的是以一个窄任务切入独立站。小型视频或字幕团队已经有视频和 SRT，发布前要确认文件能用、字幕能读完、每句话出现在正确的位置。现阶段跑通了可用原型和受控样例。真人音频上的准确性、用户节省的时间、自然流量与付费意愿仍待验证。

## 产品假设怎样变化

SRT 每条记录带序号、起止时间和正文。把字幕与视频分开，团队能单独修订字幕，并为同一视频交付不同语言的字幕轨。第一版网页支持中英文界面、中文英文和混排字幕、可调的可读性规则，并能查时间码、重叠、缺编号、短时长和超长等问题。它给出可复制的行号和时间码，适合发布前快速筛查。 [SRT 格式说明](https://www.loc.gov/preservation/digital/formats/fdd/fdd000569.shtml)

Subtitle Edit 已有免费的格式检查、视频播放、波形和时间轴工具，让单份在线格式检查的收费空间需要实际验证。探究转向更具体的交付任务。审核人员能否先看到**疑似提前或延后的字幕，再点击跳到原声复核**，从而少听大量正常片段？网站的使用价值看节省的工时和复核质量。 [Subtitle Edit 功能说明](https://subtitleedit.github.io/subtitleedit/overview.html)

## 为什么需要音频，以及这版怎样判

单看 SRT 能确定播放器**应该在哪个时间显示哪句话**。音轨提供第二份证据，帮助估计那句话**实际在什么时候说出**。同一版成片的音频和 SRT 要共用 `00:00`，并保留片头静音。

音频先在本机解码为 16 kHz 单声道。现版用 Faster Whisper 多语言 base 模型按所选语言转写并生成词级时间，处理过静音的结果会映回原音频时间轴。再按字幕原有顺序把转写和 SRT 正文匹配，中文按字、英文按词。句首、句末都能匹配且覆盖至少 70% 的文字才给出估计语音区间。找不到可靠对应的句子标为待复核。 [Faster Whisper 实现](https://github.com/SYSTRAN/faster-whisper/blob/v1.2.1/faster_whisper/transcribe.py) · [CTranslate2 音频与文字对齐](https://opennmt.net/CTranslate2/python/ctranslate2.models.Whisper.html#ctranslate2.models.Whisper.align)

在每句的开始与结束分别计算 `SRT 时间 − 估计语音时间`。负值是提前，正值是延后，任一端绝对偏差超过 0.350 秒就标出。若多句句首一致偏向同一方向，会另作整轨偏移提示。0.350 秒是原型复核阈值，是否需要改动要结合回听和交付需要判断。输入的文件仍可在原编辑器修订。

中文口播配英文字幕属于另一个验证场景。可先将原话对齐音频，再把译文按内容对应原话，允许一句对多句。当前对齐页试验的是中文配中文、英文配英文。

## 已拿到的证据

| 已做事项 | 观察到的结果 |
| --- | --- |
| 格式检查 | 浏览器验证了英文、纯中文和中英混排、Windows 换行与 BOM、异常时间码和嵌套重叠。中英文报告随界面语言切换，检查预设独立选。 |
| 两种语言各测正常、整轨偏移、单句错位 | 两份正常 SRT 均无超容差提示。人为整轨移 1.20 秒时，中文检出提前约 1.14 秒，英文检出延后约 1.27 秒。局部样例均只标记被改动的一句。 |
| 回听和复跑 | 中文第 2 句的 SRT 开始时间为 5.020 秒，语音估计 5.880 秒，报告提前 0.860 秒。浏览器已验证跳到对应语音播放和自动暂停。网页内能一键跑三类样例，对照预设改动与实测值。 |
| 修正的错误 | 修正了格式解析的错行与跨块问题。调整语音切分和留白后，合成样例的整轨误报和中文末句漏识别消除。音频上传的临时输入流改用显式读模式，并加入复测。 |

六组对齐使用的是清晰、单人合成音。模型算出来的时间应按估计值读。详细原始数据、已知误差和样例入口保存在[实测记录](RESULTS.md)。

## 继续推进的顺序

1. 找 10–20 段有权使用的真人中英录音与同语 SRT，包含口音、快语速、背景音乐、重复短句和正常对齐段。先按现在的 2 分钟上限抽样，人工标出需复核的句子和实际时间范围。分别记录误报、漏报、待复核率、人工逐段听的用时，以及使用报告定位和回听的用时。
2. 用实际省时和复核结果决定是否小范围试用。外部用户版可复用现有 Python 服务和 Faster Whisper 模型，从一个常驻 CPU 服务开始。服务器接收并暂时处理音轨和 SRT，返回句子、时间和偏差。浏览器保留用户选中的原文件用于回听。服务启动与真人素材精度是两项独立验收。
3. 观察上传、候处理与识别用时。长音频和并发开始影响体验，再以作业状态和后台队列隔开上传与处理，并按吞吐和成本实测决定是否加 GPU。对外试用时先明确访问范围和原始文件保留时长。 [后台队列适用条件](https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling)
4. 网站层面的第一项证据是同一位用户下次真的回来检查文件。之后再验证搜索获客，以及批量复核或交付报告有没有愿意付费的用户。
