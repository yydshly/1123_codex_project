# 01 独立站探索｜SRT 字幕交付检查

这是五个 AI 出海方向里的独立站探索。对象是字幕创作者和交付审核人员，试验的是一个可独立访问的小工具能否缩短发布前的质检时间。后续从 SRT 格式检查推进到同语音频对齐，产品判断、技术依据和上线条件集中在[独立站探索记录](EXPLORATION.md)。

## 本地使用与实测

用浏览器打开 [index.html](index.html)，选择或拖入一份 UTF-8 SRT，也可以先点 **试用中英双语样例**。支持中文、英文和中英混排字幕。点页顶的「中文 / English」可切换界面与报告语言。结果标注字幕编号、源文件行号和时间码，便于回到字幕编辑器修改。

打开「可读性规则」可选中文预设（每秒 10 字符、每行 18 字符）、英文预设（每秒 20 字符、每行 42 字符）或自定义。规则的选择独立于界面语言。文件在本地解析，报告可完整复制。

七份样例在 [samples](samples/) 目录。查看[实测与修正记录](RESULTS.md)，或在本目录运行 `node check-samples.cjs` 重现样例检查。

## 音频与字幕对齐

本地对齐页可以直接运行「正常对齐」「整轨偏移」「单句错位」三个样例。选择中文或英文后点样例按钮，报告会同时显示样例已知改动和软件估计的数值。比如中文单句样例只把第 2 句提前 0.900 秒，实测句首提前 0.860 秒。点语音时间戳即可回听。

使用自己的文件时，选择同一版成片的音轨和同语 UTF-8 SRT。两个文件都以成片的 00:00 为起点，音频应保留片头静音。工具按字幕文字和顺序定位对应语音，要求句首和句末找到对应，且至少匹配 70% 的汉字或英文词。无法可靠匹配的句子列为待复核。

偏差按 SRT 时间减去估计的语音时间计算。负数是提前，正数是延后。开始或结束任一端的绝对偏差超过 0.350 秒就标记，刚好 0.350 秒在容差内。这个数值用于筛查待复核的句子，是否调整以回听为准。整轨偏移提示至少要求三条匹配覆盖四分之三的有效字幕，其句首偏差都在中位数的 0.250 秒以内，且中位数本身超出 0.350 秒。

本机已装好运行依赖和模型。在此目录运行：

```powershell
python alignment_server.py
```

然后打开[本地对齐页](http://127.0.0.1:43722/align.html)，或在本地格式检查页选择「对照音频检查字幕时间」。服务只监听本机，音频在本机识别。支持 WAV、MP3、M4A，每次最长 2 分钟、最大 25 MB，最多 200 条有效字幕。

在新机器上，可从本目录执行以下命令准备依赖和模型：

```powershell
python -m pip install -r alignment-requirements.txt
python -c "from huggingface_hub import snapshot_download; snapshot_download('Systran/faster-whisper-base', local_dir='.models/faster-whisper-base', allow_patterns=['config.json','model.bin','tokenizer.json','vocabulary.txt','preprocessor_config.json'])"
```

可通过 `--model` 指向另一份本地多语言 Faster Whisper 模型。现版用模型输出的词级时间和字幕正文进行顺序匹配，两端时间均为估计值。[Faster Whisper 文档](https://github.com/SYSTRAN/faster-whisper)

[对齐样例目录](alignment-samples/)包含两段音频和六份 SRT。可直接在页面选文件回听，或用 `python check_alignment.py` 重跑本机模型验收（需要 Node.js 读取共用的 SRT 解析器）。[六组对齐实测](RESULTS.md#音频与字幕对齐实测)

## 机会和首个用户

先验证一个很窄的网站工具。把中英文 SRT 文件拖进网页，得到带时间码的质检清单。SRT 把文本和时间码存在视频之外，团队可以独立修订字幕、交付不同语言的字幕轨。首批用户选小型字幕制作团队和经常向客户交字幕的自由职业者。特别值得问的是，交审前每周要检查几次，审稿人有没有刚好只想检查或共享错误清单的场景。

现成的 Subtitle Edit 已经能检查阅读速度、行长、时长和重叠，也支持导出。因此，这个网站的价值假设应落在工作流程上。比如项目经理没有安装编辑软件，或者多位审稿人需要打开同一份规则并把问题发回给制作者。访谈时请对方现场演示现有做法，才能知道浏览器工具究竟省掉了哪一步。 [Subtitle Edit 的错误列表功能](https://subtitleedit.github.io/subtitleedit/features/list-errors.html)

## 最小交付与验收

一页做完「选文件 → 出结果 → 定位问题」。首版选择 UTF-8 的 SRT。按序号、起止时间、问题原因显示结果，提供复制清单。文件在浏览器本地解析。可配置的阅读速度、行长和时长作为提醒，先把无法解析、结束早于开始、相邻时间重叠等问题报清楚。阈值按用户的交付标准设定。

准备用于验收的样例包括正常字幕、混合中英文、UTF-8 BOM、不同换行符、空字幕、损坏时间码和多行字幕。用人工标注的答案对照问题位置和数量，确认正常文件不会被误报为错误。首批用户应该能从提示直接找到原文件中需要改的段落。

## 七天试验

| 时间 | 行动 | 留下的证据 |
| --- | --- | --- |
| 第 1 天 | 搜索 `srt overlap checker`、`subtitle QC report`，记录现有做法和替代工具。找 5 位真实处理字幕的人，问上一次交付和质检耗时 | 最近一次任务、频率、返工原因、现有工具 |
| 第 2–3 天 | 做一页原型和一份故意出错的样例，找两位用户现场试 | 能否独立完成、找到问题所需时间、误报 |
| 第 4–7 天 | 让 5 位用户拿自己的文件试，邀请有批量任务的人以固定价试用批量检查或导出 | 真实文件检查数、用报告修订的人数、第二次使用、付费意向或付款 |
| 第 2–4 周 | 有实际使用后，写一个对应用户常搜问题的英文页面，设置 Search Console | 搜索词、展示、点击、检查完成和付费，按来源分别记录 |

## 收入和限制

单文件检查可作为获客入口。先试固定价格的批量处理或一次性报告。等用户证明每月持续使用，再评估月费。广告需要持续流量，也会占据工具页面，首轮优先验证客户为何会付费。

情景演算采用月访客 2,000 人，其中 40% 完成检查，完成者中 5% 开始结账，结账者中 25% 付款。最终是 10 笔交易。按每笔 12 美元计算，月毛收款为 120 美元，再扣支付、托管和支持成本。比例和价格均为假设，用来说明流量与转化分别有多大影响。

## 继续投入的条件

- **继续做**。首轮 5 人里至少 3 人能独立检查真实文件，至少 2 人用清单修了字幕，另有 1 人在真实任务中再次使用或为批量功能付款。复用信号支持继续改工具，实际付款才支持收费假设。
- **改产品**。检查完成率高但用户拿结果时还得自己整理，优先调整报告。用户都只查一次，可以试一次性付费或转向文件量更大的客户。
- **暂停这个切口**。如果连续访谈发现现有编辑工具已经顺手解决同一问题，而且团队也没有交接开销，就把精力转到记录里反复出现的其他痛点。

**第一场测试只需要一个问题**。请用户把上次返工的字幕拿出来，现场比较原有检查方式和网页检查方式各用了几分钟、发现了几个确实要改的问题。
