# 04 自动化服务｜广告周报对账

## 阶段总结

**定位。** 这是一个面向投放代运营团队的周报汇总和复核工作台。经办人导入 Google Ads、Meta Ads 的每日明细和同周旧报，工作台匹配字段、汇总指标、核对口径、标出差额并导出草稿。完整对账需要同周旧报，每个平台按一个账户处理。发票、平台账单和付款记录属于财务对账场景。

| 实际能力 | 省掉的手工步骤 | 仍需经办人完成 |
| --- | --- | --- |
| 识别常见中英表头，清理平台汇总和重复行，按平台汇总 | 复制两份 CSV 到同一张表、删汇总行、逐列写求和公式 | 从广告后台按正确的日期、币种、时区和广告系列层级导出 |
| 并排比较同口径的旧值和本次值，把点击和转化口径冲突列为待复核 | 逐格比对、手工找出要重查的指标 | 确认事件定义、归属日期与归因窗口，必要时按相同口径重导 |
| 追到旧报单元格、原文件列、广告系列与明细行，导出复核草稿 | 在三份文件之间来回查列、复算本次值、整理复核清单 | 用历史明细判定差额成因，确认报告后交付 |

**证据。** 拟真样例从两路共 6 条有效明细算出 809.00 美元，查出 1 处同口径数值差异和 3 处口径差异。实测验证了上表这些操作可以交给工作台，真实客户的净省工时和付费意愿仍待验证。 [实测与来源追溯](RESULTS.md#拟真导出回放与差异追溯)

**值得做的场景。** 每周给多家客户交报告、经常合并两个广告后台、需要交付前二次复核的代运营团队，最有可能节省工时。单一账户、只看后台数字或每月偶尔出一张表的场景，节省空间有限。由于要有一份同周旧报，当前收益主要来自复核与追溯，首份周报的完整制作仍在现有流程内。

**阶段决定。** 保留可用原型，暂缓扩展。下一次判断投入以真实团队的一周历史复跑为起点，记录从导入、补证到复核完成的工时，以及团队是否愿意下周继续用。

## 网页工作台

面向每周给客户做投放汇报的小型营销代理。每周换上新文件，工作台会核验指标口径，汇总两路投放数据，与同周旧周报逐项对账，并生成一份可编辑的 Markdown 周报草稿。核心能力是**让周报数字可复算、差异可追溯**。发票识别属于财务流程，通常要核对发票、广告平台账单与付款记录。

**打开工作台**。[广告周报工作台](http://127.0.0.1:43728/)

在本目录运行 `python -X utf8 -B server.py` 可重新启动。服务在本机运行，浏览器只保存已用过的列匹配，原始文件和草稿不会写入服务目录。

1. **设范围**。填写周起始日、币种和时区。范围包含起始日及之后六天，每个平台一个账户。
2. **导入三份文件**。Google Ads、Meta Ads 按日期和广告系列导出每日明细 CSV。旧周报用 CSV 或现有对账 JSON。旧 CSV 每个平台一行，基本格式为 `周起始日,平台,广告账户编号,币种,时区,花费,展示,点击,转化`。旧报缺范围或账户信息时，核实后可在对应卡片勾选确认。
3. **检查字段和口径**。展开卡片可改映射或重新指定表头行。明细缺少账户 ID、币种或时区时，可填写该文件实际使用的值。点击列可识别部分明确表头。转化需要根据账户设置填写事件、归属日期、归因窗口，以及影响核验的归因模型或计数方式。旧 CSV 可增加 `点击口径,转化口径` 两列，旧 JSON 可在每个平台的记录内增加 `clicks_scope`、`conversions_scope`。两边用统一写法记录已核实的同一口径。
4. **运行对账，追溯差异**。同口径才计算差额。口径不同或缺失时保留两边原值，暂停该项数值对账。点「查看来源」可以看到旧报单元格或 JSON 字段，以及本次统计的原文件、列、账户、广告系列、日期和行号。页面最多展示每项前 20 条计入的明细。导出的 Markdown 草稿也带来源定位。
5. **重复使用**。点「开始新一周」清空当前输入。下次用同一平台、相同表头的文件会沿用上次成功运行的列映射。本周平台设置由经办人核实。

点「载入口径对账样例」可重跑包含真实风格表头、归因窗口和冲突口径的模拟周报。样例 CSV 保存于 `samples/metric-scopes/`，也可通过文件选择器导入。客户数据、签收后的净省工时仍待试点验证。 [实测记录](RESULTS.md)

## 首版试点与现有证据

服务卖给需要每周给客户汇报投放表现的小型营销代理。首单的验收目标是拿到一周历史文件，合并两路导出后让客户逐项复核，并把导入、查异常和人工复核都计入耗时。

本地试点已跑完 Google Ads 和 Meta Ads 两份模拟导出，以及一份模拟历史周报。用 `python -X utf8 -B check_trial.py` 重现。实际报告为 Markdown 草稿，包含各来源花费、展示、点击、CTR、归因转化、CPA 和待复核项。 [实测报告与案例](RESULTS.md)

## 接入一周真实数据的最小规格

| 交接项 | 试点口径 |
| --- | --- |
| 对象 | 一个客户，每个平台选一个账户。先由负责人确认账户与客户的归属。 |
| 周范围 | 明确起始日及后续六日，重现历史周报使用的账户时区、币种和日期口径。 |
| 输入 | 两份原始导出和一份已确认的历史周报。在工作台确认字段映射和统计口径。 |
| 计算 | 一行对应一个账户、一个广告系列、一天。CTR 用合计点击除以合计展示。CPA 用平台花费除以该平台归因转化。 |
| 对账 | 花费、展示、点击和转化逐平台比较。点击或转化口径不同及未提供时列为待复核。统一币种下计算合计花费。 |
| 验收 | 负责人能从草稿追查差异和异常行。用同一批文件再次执行时，结果可复现。省时以对方实际复核和修改完成后的工时为准。 |

Google Ads 支持选择报表列并下载 CSV。选用默认转化列或按转化时间列，会改变转化归属的统计日期。Meta Ads Insights 也有归因和报告时间口径。真实试点先在两边记下选用的转化指标、日期归属与窗口，再锁定字段。 [Google Ads 报表下载](https://support.google.com/google-ads/answer/2404036?hl=en-en) · [Google Ads 转化口径](https://support.google.com/google-ads/answer/6270625) · [Meta 报告口径](https://developers.facebook.com/docs/marketing-api/insights/best-practices/)

当前脚本的输入是按约定整理过的 UTF-8 CSV，表头为 `date,account_id,campaign_id,currency,timezone,spend,impressions,clicks,conversions`。明细的日期和时区填写为导出所用口径。花费和转化允许小数，点击和展示用整数。历史对账 JSON 写入 `week_start`、`currency`、`timezone`，并在 `google` 和 `meta` 下分别填写 `account_id` 和四项汇总指标。格式与测试数据可查 [试跑脚本](check_trial.py)。用准备好的文件运行 [周报脚本](weekly_report.py)：

```powershell
python -X utf8 weekly_report.py --google google.csv --meta meta.csv --week-start 2026-11-09 --currency USD --timezone Asia/Shanghai --reference reference.json
```

## 客户、流程与交付承诺

先服务每周手工合并广告报表的小型营销代理。试点只处理一个客户、两个广告来源、一周数据。客户提供导出的 CSV 和一份已确认的旧周报，交付对账结果、异常列表和可供复核的周报草稿。Google Ads 支持 CSV 报表下载，第二个来源由试点客户用已有导出提供。 [Google Ads 报表下载说明](https://support.google.com/google-ads/answer/2404036?hl=en-en)

付款理由是流程每周重做，答复的是三个可量化的问题。手工下载、合并、核对和改文案各用了多久？现在复核和例外处理耗时多少？报表能不能用同一套规则给第二个客户做？客户节省的是每周花掉的有效工时，服务方要测维护会不会吃掉收入。

## 从历史试点到可维护流程

1. **取得基线**。请客户录一次现有做法，计时并记录币种、时区、统计区间、归因口径、字段含义和异常处理。约定哪些数字是验收字段以及报告由谁确认。
2. **固定规则**。只接约定字段。按客户、来源和报告周标识输入。聚合金额与计数前检查币种、日期和重复数据。按客户同意的口径计算点击率和每次转化成本。口径不同的转化分平台展示。
3. **生成草稿**。报表数值来自固定规则。AI 可以基于确认过的数字起草摘要，客户复核后发布。对缺列、重复导入、超出周区间或币种不符的数据给出可定位的错误。
4. **回放再上线**。用历史周报验证总额，同时跑一份有缺列的输入和一次重复运行，观察错误是否会被看见、同一批数据是否只生成一个对应结果。再让一位客户同事用下一周的数据试跑。
5. **确认运行负责人**。先用手动导入跑通。后续若用 Apps Script 定时生成，安排客户认可的账号创建触发器，明确异常发到哪里。安装式触发器以创建者账号运行，服务也有配额。 [Apps Script 安装式触发器](https://developers.google.com/apps-script/guides/triggers/installable) · [Apps Script 配额](https://developers.google.com/apps-script/guides/services/quotas)

## 价值和报价演算

假设原来每周花 1 小时 45 分钟，试点后的导入和复核花 30 分钟，每月做 4 次，人工成本按 30 美元每小时计，则客户每月节省约 150 美元的工时。自动化之后仍要处理的异常，要计入每周耗时。

可以用 150 美元试单报价做第一轮测试。若首单实际花 5 小时，扣工具费前约 30 美元每小时，再看前期获客耗时。如果持续服务试价为每月 79 美元，月维护 1 小时按 30 美元计，工具成本假定每月 10 美元，每月还剩 39 美元覆盖沟通、获客和利润。价格与工时都是测算输入，应用实测替换。

## 继续投入的条件

- **适合续费**。关键字段对账在约定误差内，客户把草稿用于实际交付，连续两次运行都显著省时，实际维护工时可控。
- **适合收窄**。同一来源反复变字段、异常处置超过预计，先锁定报表格式和渠道，进行一次复测。
- **适合暂停**。客户已有顺手的报表流程，每周只花几分钟，或者节省出来的时间都被复核占回去。转找频率更高或跨来源合并成本更高的团队。

**第一个要拿到的证据**是一份历史周报和两个来源的同周 CSV。对上数据并量出复核时间后，才有依据谈下周是否继续跑。
